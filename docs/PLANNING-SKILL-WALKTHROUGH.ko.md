# goal-loop-planning 스킬 재구성: 두 질문으로 따라간 사례 (1차)

- 작성일: 2026-11-13
- 관련 기록: aim-19(goal-loop-planning 스킬), goal-156·157, proposal-202(불합격 뒤 안내 수정), proposal-205(짧은 기한의 판정 비용)
- 상태: 1차(두 질문 중심)와 2차(2×2 유형 표 중심)를 비교했고, 그 해석으로 스킬을 다시 쓰기로 했습니다(2026-11-13).

## 왜 다시 따라갔는가

처음 작성한 스킬은 세 가지 틀(유기적 자문자답과 무기적 검증의 두 질문, 회고의 교훈, 문제 유형 2×2 표)을 연결 없이 쌓아서 논리가 이어지지 않았습니다. 사용자가 정리한 흐름은 다음과 같습니다.

1. 회고 내용에는 문제 유형 파악이 가깝다.
2. 두 질문은 Goal Loop를 만들 때 바탕에 둔 사고법인데, 도구에서 빠져 있다.
3. 도구를 크게 고치기보다 스킬로 사용법을 보완한다.

그래서 기업 보고서 질의응답 에이전트 사례를 처음부터 두 질문만으로 다시 따라가 보았습니다.

## 사례의 조건

- 기업 보고서(사업보고서, 반기보고서 등)를 읽고 질문에 답하는 AI 에이전트를 만드는 시험입니다.
- 질문 예시: "SK하이닉스와 삼성전자의 공통 고객은 어디이고 규모는 얼마나 되는가?", "휴맥스는 삼성전자와 SK하이닉스의 고객사인가?"
- 기한은 5시간입니다. 채점 방식과 합격선은 알려지지 않았습니다.
- 에이전트와 함께 챗봇 UI를 HTML로 만들어야 합니다. HTML을 로컬에 만들어 두면 자동으로 제출됩니다.
- 보고서는 PDF와 HTML이 섞여 있고 양이 많습니다. 예시 질문의 근거에는 익명 표기와 별칭이 섞여 있습니다.

## 따라간 결과로 나온 구조

```
aim-1  5시간 안에, 기업 보고서를 근거로 질문에 답하는 에이전트를 챗봇 UI로 쓸 수 있게 제출한다
├─ Goal 1    문서 텍스트화와 자체 평가 세트                       (0:00–0:45)
├─ aim-1.1   UI에서 쓸 수 있는 에이전트를 만들고, 정답률을 높인다  (0:45–4:30)
│   ├─ Goal 1.1-1  기준선 에이전트                               (0:45–1:15)
│   ├─ Goal 1.1-2  HTML 연결: 이 시점부터 제출할 수 있음         (1:15–1:45)
│   └─ Goal 1.1-3…  측정된 오답 원인마다 하나씩, 그때 만든다      (1:45–4:30)
└─ Goal 2    HTML에서 예시 질문 확인                              (4:30–5:00)
```

aim-1의 기준: 필수 요건(챗봇 UI에서 답한다, 기한 안에 제출한다), 측정(자체 평가 세트의 정답률), 목표(숫자 없음, 남은 시간 동안 오답을 줄임), 멈춤(4:30), 한계(자체 평가 세트의 점수가 실제 점수를 보장하지 않음).

aim-1.1의 기준: 1:45까지 UI에서 답하는 에이전트를 만들고, 4:30까지 정답률을 기준선보다 높인다. 측정은 Goal 1의 평가 스크립트로 한다. Goal마다 측정된 오답을 인용하고 가장 큰 원인 하나만 고친다. 되돌릴지는 문항별 변화로 판단한다. 두 번 연속 정체하면 되돌아본다.

## 단계마다 나온 것

### Aim을 정할 때
- 자문자답으로 원하는 것을 좁힌다. 원하는 것은 "프로그램"이 아니라 "시험의 결과"였다.
- 무기적 검증으로 후보 문장을 거른다. "이것이 이루어지면 끝나는가?"
- "끝났는지 무엇으로 아는가?"에 답할 수 없으면 대리 지표를 만들고, 그 한계를 기준에 적는다.
- 바깥 조건(기한, UI)은 "어기면 끝나지 않는가?"로 넣을지 정한다. 합격선이 없으면 멈춤 조건은 시간이다.
- 예상되는 어려움은 기준에 넣지 않고 후보로만 둔다.

### 나눌 때
- 계약으로 쓸 수 있으면 Goal, 방향은 있지만 계약은 측정한 뒤에야 쓸 수 있으면 Aim으로 둔다.
- Aim은 활동이 아니라 바뀌는 대상을 가리킨다. Aim 바깥의 산출물에 기대면 기준에 적고 의존으로 건다. (처음에 aim-1.1을 "오답 줄이기"로 두었다가, 에이전트와 UI를 만드는 일이 Aim 바깥에 있어서 사용자가 이상하다고 지적했다.)
- 자문자답: 지금 이유를 댈 수 있는 것만 만든다. 출제자가 요구한 UI도 관찰된 이유다.
- 무기적 검증: 시점마다 "여기서 멈추면 끝나는가?"를 묻고, 제출할 수 있는 상태를 앞당긴다.
- Goal은 실패했을 때 원인을 알 수 있을 만큼 작게 나눈다.

### 원인을 좁힐 때 (기준선 결과는 가정)
- 실행 기록에서 가장 큰 원인 하나를 고른다.
- 가장 값싼 확인부터 한다: 관찰, 실험(정답 근거를 직접 넣어 보기), 구현의 순서다.
- "끝나는가?"에는 부작용(다른 문항이 망가지는지)도 포함된다.

### 확인 결과가 '아니오'일 때 (가정)
- 배제된 가설을 기록한다(그 Proposal을 실험 결과를 근거로 닫는다).
- 실험으로 알게 된 사실이 다음 후보를 바꾼다(근거가 이미 모델 앞에 있었다면 검색이 아니라 유보 규칙이나 근거의 상태를 본다).
- '아니오'가 두 번 이어지면 측정(평가 세트의 정답)을 의심한다.

### 개선이 오르지 않을 때 (가정)
- 총점이 아니라 문항별 변화를 본다. 작은 평가 세트에서는 하나를 고치고 하나를 망가뜨리면 총점이 그대로다.
- "왜 고쳐도 오르지 않는가?"로 자문자답의 대상을 한 단계 올린다.
- 구조를 추가할 근거는 여기서 처음 생긴다(둘 이상의 오답이 같은 원인, 작은 수정의 실패, 실험으로 확인한 효과).
- 멈추거나 평가 세트를 넓히는 것도 선택지다.

### 판정과 기록
- 기한이 짧으면 Goal의 판정은 평가 스크립트의 출력으로 기계적으로 하고, 위임 판정은 Aim 평가에만 쓴다(proposal-205).
- 실행 실패는 `retry-decide`, 판정 미충족은 같은 Contract의 보완 Attempt로 처리한다(proposal-202).

## 이 결과로 제안한 스킬 구성

0. 목적과 한계 / 1. 두 질문 / 2. Aim을 정할 때 / 3. 나눌 때 / 4. 원인을 좁힐 때 / 5. 확인 결과가 '아니오'일 때 / 6. 개선이 오르지 않을 때 / 7. 판정과 기록.
같은 두 질문을, 일이 진행되는 시점마다 다르게 던지는 구조입니다.

## 정하지 않은 것

1. 진행 순서를 뼈대로 삼을지
2. 문제 유형 2×2 표를 뺄지 (이번에는 유형을 먼저 정하는 단계가 필요하지 않았고, 이분법보다 "어디까지 아는가"가 쓸모 있었다)
3. 사례를 스킬 본문에 둘지 (같은 과제로 효과를 측정하면 결과가 오염되므로, 효과 확인 실험은 다른 과제로 한다)

## 근거의 수준

사례 하나를 따라가며 얻은 결과입니다. 기준선 결과, 오답 분포, 실험 결과는 가정했습니다. 회고의 원인("근거가 모델에 도달하지 않았다")도 기억에 기댄 가설입니다.

# 2차: 2×2 문제 유형 표를 중심으로 같은 사례를 따라감

두 질문은 쓰지 않고, 유형 표와 유형별 방법만 썼습니다. 기준선과 오답 분포는 1차와 같은 가정입니다.

## 단계마다 나온 것

- **Aim의 유형:** 표는 이미 있는 Aim을 분류할 뿐입니다. "프로그램을 완성한다"에 적용하면 "완성은 돌아가는지만 보면 확인된다"는 이유로 구축형이 되고, 구성 요소별 분할로 원래 실패가 그대로 재현됩니다. **표는 잘못 정의된 Aim을 고치지 못하고 굳힙니다.** 결과로 정의한 aim-1에 적용하면 하나의 유형으로 분류되지 않고, 부분마다 유형이 다릅니다.
- **나누기:** 부분마다 분류하면(텍스트화·평가 세트·UI는 구축형, 정답률은 탐색형, 오답마다 원인 규명형) 1차와 거의 같은 구조가 나옵니다. 표는 "구축형이면 Goal, 탐색형이면 Aim"으로 Aim과 Goal을 명확하게 가릅니다. 그러나 순서(UI를 언제 만드는가)는 정하지 못합니다.
- **오답이 나왔을 때:** 표는 "만드는 일에서 진단하는 일로 바꾸라"는 신호를 분명히 줍니다(원인 규명형에 구축형의 방법을 쓰지 않는다). 그러나 무엇부터 고칠지 정하지 못하고, 오답을 분포가 아니라 하나씩 보게 하며, 원인을 좁히는 절차는 두 질문을 빌려야 합니다.
- **'아니오'가 두 번일 때:** 유형을 다시 판별하면 "고쳐졌는지 바로 확인되는가"가 흔들립니다(정답이 애매함). 1차의 "측정을 의심한다"가 "유형을 다시 판별한다"는 하나의 동작에서 나옵니다.
- **정체할 때:** 표에는 정체 규칙이 없습니다. 그러나 남은 공통 고객 문항을 다시 판별하면, 관찰로 해법을 알게 되어 구축형으로 바뀝니다. 1차의 "구조를 추가할 근거는 정체에서 생긴다"가 "구조를 알게 된 부분이 구축형으로 옮겨 간다"로 설명됩니다.

## 비교

| 일 | 두 질문 중심(1차) | 유형 표 중심(2차) |
|---|---|---|
| Aim 정의 | 합니다 | 못 합니다(잘못된 Aim을 굳힘) |
| Aim과 Goal 가르기 | 즉석에서 판단했고, 한 번 틀림 | 명확합니다 |
| 순서와 우선순위 | 정합니다 | 정하지 못합니다 |
| 만들기에서 진단으로 전환 | 따로 신호는 없음 | 분명한 신호를 줍니다 |
| 원인 좁히기 | 합니다 | 절차가 없어 두 질문을 빌립니다 |
| 한 단계 위로 올라가기 | 따로 세운 규칙 | 유형을 다시 판별하는 동작에서 나옵니다 |
| 구조를 추가할 때 | 따로 세운 규칙 | 구조를 알게 된 부분이 구축형으로 옮겨 갑니다 |

## 해석 (사용자와 합의, 2026-11-13)

- **유형은 문제의 고정된 성질이 아니라, 지금 아는 정도입니다.** 같은 공통 고객 문항이 탐색형에서 원인 규명형을 거쳐 구축형이 되었습니다. 일이 진행된다는 것은 부분들이 구축형으로 옮겨 가는 과정입니다.
- **두 질문은 엔진이고, 유형 표는 지도입니다.** 두 질문을 매 시점에 던지고, 그 답으로 지금 아는 정도(유형)를 표시하며, 유형이 기록 방법(Aim 또는 Goal, 진단 또는 구현, 판정 방법)을 알려 줍니다.
- 표의 두 축은 두 질문으로 답합니다. "구조를 아는가?"는 "지금 이유를 댈 수 있는가?(자문자답)"로, "한 번에 확인되는가?"는 "끝났는지 무엇으로 아는가?(무기적 검증)"로 답합니다.
- 순서가 있습니다. 표가 제대로 작동하려면, 먼저 두 질문으로 Aim이 올바르게 정의되어 있어야 합니다.
